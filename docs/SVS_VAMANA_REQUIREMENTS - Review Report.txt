EXECUTIVE SUMMARY
--------------------------------------------------------------------------------
The requirements document is technically detailed and covers the happy-path
functional requirements well. However, it has three critical structural gaps:
(1) all stakeholder review and approval fields are "TBD," meaning no formal
sign-off has occurred; (2) several MUST requirements are directly contradicted
by the companion C API document (notably memory limit enforcement and pg_upgrade
compatibility), indicating the requirements were not kept in sync with
implementation; and (3) security, DR, and operational readiness sections are
sparse to non-existent for a system that stores index data outside the
PostgreSQL data directory and runs third-party native code in-process. The
SDL 201 threat model plan is a good planning artifact but contains no completed
threat model, and the SAFE review inputs are largely missing.

REQUIREMENT: FR-1.4.1 — Insert Support (Incremental Updates)
--------------------------------------------------------------------------------

  Description:
    New vectors are inserted incrementally via SVSAddPoints without a full
    rebuild; inserts are immediately available in queries; <5ms per vector.

  Reviewer Comments:
    "New vectors immediately available in queries" — does this mean visible
    before the INSERT transaction commits? In PostgreSQL, index entries must
    not be visible before the inserting transaction commits (MVCC). This
    statement appears to conflict with standard MVCC semantics. Clarify:
    "Vectors inserted in a committed transaction are visible in subsequent
    queries in the same or later snapshots."

    "Two-tier architecture" with a "delta buffer" is described, but no
    requirement exists for the delta buffer's durability (is it persisted to
    disk before the INSERT returns?). The C API doc shows the dynamic index is
    held in memory and saved via SVSSaveIndex with needsSave=true — but when
    is this save triggered? On transaction commit? On checkpoint? This is a
    data durability gap.

    The advisory lock (VAMANA_DYNAMIC_WRITE_LOCK_KEY) mentioned in the C API
    doc is not referenced here. A requirement should specify lock acquisition
    behavior: "INSERT operations acquire an exclusive advisory lock on the
    index before calling SVSAddPoints; the lock is released after the call
    returns, before transaction commit."

    Bulk insert via svs_index_add_batch() is listed as a method but the C API
    doc notes "SVSAddPoints is called once per row; potential future
    optimization" — this is inconsistent with the stated batch support.

REQUIREMENT: FR-1.4.3 — Delete Support
--------------------------------------------------------------------------------

  Description:
    Deleted vectors are excluded from query results; space is reclaimed after
    VACUUM; delete completes in <1ms.

  Reviewer Comments:
    The C API doc explains tombstone semantics: SVSDeletePoints marks entries
    with tombstones; the search path filters on InvalidItemPointer; consolidate
    + compact happen during VACUUM. This is a well-designed approach, but the
    requirements don't mention what happens when the tombstone ratio is high
    before VACUUM runs — specifically: does recall degrade significantly with
    many tombstones? If so, a requirement should specify a maximum recommended
    tombstone ratio before forced VACUUM.

    "Space is reclaimed after VACUUM" — the C API doc shows compact only runs
    when deleted fraction exceeds vamana.compact_threshold_pct (default 10%).
    The requirements should disclose this threshold behavior, as it means space
    is not reclaimed immediately after every VACUUM.

REQUIREMENT: FR-1.4.4 — Bulk Operations
--------------------------------------------------------------------------------

  Description:
    Bulk insert/update/delete operations are more efficient than individual
    operations; bulk insert >10,000 vectors/second.

  Reviewer Comments:
    The C API doc explicitly notes batch insert is a "potential future
    optimization" (SVSAddPoints is called once per row). The ">10,000
    vectors/second" target cannot currently be met via the batch API if it
    doesn't exist. This requirement should either be labeled as FUTURE or
    have an issue filed against it. The current implementation at 1 row per
    call with <5ms per vector implies a maximum of ~200 vectors/second, not

  DL-2: REQUIREMENTS vs. IMPLEMENTATION GAP (STATUS INFLATION)
  -------------------------------------------------------------
  The document repeatedly marks items as "✅ COMPLETE" or "Implementation
  Complete" in the header, while the body text contains unchecked checklist
  items and known gaps. This creates a misleading document state. Four
  specific gaps where the status is inflated:
  - maintenance_work_mem enforcement (stated as required, not implemented)
  - pg_upgrade support (stated as MUST, explicitly unverified in C API doc)
  - svs_index_add_batch() batch insert (stated as implemented, noted as
    "future" in C API doc)

  Recommendation: Add a "Known Limitations" section listing these items with
  tracking issue numbers. Do not mark a requirement as ✅ COMPLETE if its
  acceptance criteria contain unverified items.
